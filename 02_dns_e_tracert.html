Tutorial 1 · Il protocollo DNS

Tutorial 1 di 2

Il DNS (Domain Name System) è il sistema che traduce i nomi di dominio leggibili dall'uomo (come www.google.com) in indirizzi IP numerici (come 142.250.180.68) che i computer usano per comunicare. Senza DNS dovremmo ricordare indirizzi IP a memoria.

Struttura gerarchica del DNS

Il DNS è organizzato come un albero rovesciato. Alla radice ci sono i Root Server (13 cluster nel mondo), poi i TLD Server (Top-Level Domain: .com, .it, ecc.) e infine i Authoritative Name Server di ogni dominio.

Fig. 1 – Gerarchia del DNS: da Root Server agli Authoritative Name Server

Il processo di risoluzione DNS (query ricorsiva)

Quando digitate www.google.com nel browser, il vostro PC non conosce l'indirizzo IP. Avvia quindi una query DNS ricorsiva: chiede al resolver locale (solitamente il router o un server del provider), che a sua volta consulta la gerarchia di server fino ad ottenere la risposta.

Fig. 2 – Il resolver esegue la query ricorsiva per conto del client (frecce blu = query, verdi = risposta)

Struttura di un pacchetto DNS

I messaggi DNS viaggiano su UDP porta 53 (o TCP se la risposta supera 512 byte). Ogni messaggio contiene:

  • Header – ID transazione, flag (Query/Response, Authoritative, ecc.), contatori.
  • Question section – il nome richiesto e il tipo di record (A, AAAA, MX, ecc.).
  • Answer section – la risposta con l'indirizzo IP e il TTL (Time To Live).
Tipo di record Significato Esempio
AIndirizzo IPv4google.com → 142.250.x.x
AAAAIndirizzo IPv6google.com → 2a00:1450:...
MXMail server del dominiogoogle.com → smtp.google.com
CNAMEAlias verso un altro nomewww.google.com → google.com
NSName Server autoritativogoogle.com → ns1.google.com
💡 Il TTL e la cache DNS Ogni risposta DNS include un valore TTL (Time To Live, in secondi): indica per quanto tempo il resolver può tenere in cache la risposta. Se fate la stessa query entro il TTL, il resolver risponde dalla cache senza contattare nuovamente i server — per questo potreste non vedere traffico DNS in WireShark!

Esercizio 1 · Catturare query DNS con WireShark

Tutorial 1 · Parte pratica

In questo esercizio osserverete in diretta come il vostro PC risolve un nome di dominio. Cattureremo le query DNS generate dal comando nslookup e le analizzeremo in WireShark, identificando i pacchetti di richiesta (Query) e di risposta (Response).

Fig. 3 – WireShark intercetta la query DNS e la relativa risposta sull'interfaccia di rete attiva

⚠️ Prima di iniziare: svuotare la cache DNS Se la risposta è già in cache, il vostro PC non invierà nessuna query DNS e non vedrete nulla in WireShark! Svuotate la cache prima di ogni cattura con il comando:
ipconfig /flushdns

Istruzioni passo-passo

  1. Aprire il Prompt dei Comandi come Amministratore Cliccate su Start, digitate cmd, fate click destro su "Prompt dei comandi" e scegliete Esegui come amministratore. Servono i permessi admin per svuotare la cache DNS.
  2. Svuotare la cache DNS Nel prompt digitate: 
    ipconfig /flushdns
    Dovreste vedere il messaggio: "Svuotamento della cache del resolver DNS completato".
  3. Trovare il proprio indirizzo DNS Digitate nel prompt: 
    ipconfig /all
    Cercate la riga "Server DNS" e annotatevi l'indirizzo IP (es. 192.168.1.1 oppure 8.8.8.8). Questo è il server a cui il vostro PC farà le query DNS.
  4. Avviare WireShark e selezionare l'interfaccia attiva Aprite WireShark. Nella schermata iniziale identificate l'interfaccia con il grafico animato (Ethernet o Wi-Fi) e fate doppio click per avviare la cattura.
  5. Applicare il capture filter (opzionale ma consigliato) Prima di avviare la cattura potete scrivere nella barra del capture filter: 
    udp port 53
    Così catturate solo il traffico DNS e la lista rimane leggibile.
  6. Eseguire una query DNS con nslookup Tornate al prompt e digitate: 
    nslookup www.google.com
    Poi eseguite anche: 
    nslookup www.wikipedia.org
    nslookup forza una query DNS indipendentemente dalla cache del browser.
  7. Fermare la cattura in WireShark Premete il pulsante ■ Stop (o Ctrl+E).
  8. Applicare il display filter DNS Nella barra dei filtri digitate: 
    dns
    Vedrete coppie di pacchetti: una Standard query (Query) e una Standard query response (Response) per ogni dominio richiesto.
  9. Analizzare i pacchetti Cliccate su una Standard query e nel pannello centrale espandete:
    • User Datagram Protocol → verificate porta sorgente (casuale >1024) e destinazione (53)
    • Domain Name System (query) → espandete Queries: vedrete il nome richiesto e il tipo (A)
    Poi cliccate sulla Standard query response e espandete:
    • Domain Name System (response) → espandete Answers: vedrete l'indirizzo IP e il TTL
✅ Cosa dovreste vedere in WireShark
  • Pacchetto Query: dal vostro IP verso IP DNS, UDP porta 53, tipo A per www.google.com
  • Pacchetto Response: dal DNS verso il vostro IP, con uno o più indirizzi IPv4 nella sezione Answers
  • Eventuale query AAAA (IPv6) in parallelo alla query A

Verifica – Lista di controllo

Spuntate ogni punto dopo averlo completato:

  • Ho svuotato la cache DNS con ipconfig /flushdns
  • Ho annotato l'indirizzo del mio server DNS con ipconfig /all
  • Ho avviato la cattura su WireShark sull'interfaccia corretta
  • Ho eseguito nslookup www.google.com e nslookup www.wikipedia.org
  • Applicando il filtro dns vedo coppie Query/Response
  • Ho identificato la porta 53 UDP nella query
  • Ho trovato l'indirizzo IP di google.com nella sezione Answers della response
  • Ho letto il valore TTL della risposta (in secondi)
🎉 Ottimo lavoro sul Tutorial 1! Hai osservato il DNS all'opera: query UDP verso la porta 53, risposta con l'IP richiesto e il TTL. Procedi ora con il Tutorial 2 su Tracert!

Tutorial 2 · Il comando Tracert

Tutorial 2 di 2

tracert (su Windows; traceroute su Linux/macOS) è un comando che mostra il percorso che i pacchetti compiono dalla vostra macchina fino a una destinazione, elencando tutti i router intermedi (hop) attraversati. È uno strumento fondamentale per la diagnosi di problemi di connettività.

Il meccanismo: TTL e ICMP Time Exceeded

tracert sfrutta in modo ingegnoso il campo TTL (Time To Live) dell'header IP. Ogni router che riceve un pacchetto decrementa il TTL di 1. Se il TTL arriva a 0, il router scarta il pacchetto e invia al mittente un messaggio ICMP Type 11 – Time Exceeded. Questo messaggio contiene l'IP del router che ha scartato il pacchetto — ed è esattamente quello che tracert usa per mappare il percorso.

Fig. 4 – Tracert aumenta il TTL di 1 ad ogni sonda: ogni router che esaurisce il TTL risponde con ICMP Time Exceeded

Algoritmo di Tracert passo-passo

Per ogni hop (da 1 fino a un massimo, di default 30), tracert:

  1. Invia 3 pacchetti ICMP Echo Request (o UDP su Linux) con TTL uguale al numero dell'hop.
  2. Aspetta fino a 3 secondi una risposta da un router o dalla destinazione.
  3. Misura il tempo di andata e ritorno (RTT) in millisecondi per ognuno dei 3 pacchetti.
  4. Se riceve ICMP Time Exceeded → annota l'IP del router e passa all'hop successivo.
  5. Se riceve ICMP Echo Reply dalla destinazione → il tracciato è completato.
  6. Se non riceve risposta entro il timeout → stampa * * * (hop non risponde, spesso firewall).

Fig. 5 – Ogni hop risponde con ICMP Time Exceeded; WireShark cattura tutta la sequenza

💡 Hop con * * * nel tracert Alcuni router sono configurati per non rispondere ai messaggi ICMP (per sicurezza o policy di rete). In WireShark vedrete comunque i pacchetti in uscita, ma nessuna risposta in ingresso per quell'hop. Questo non significa che il percorso sia interrotto: i pacchetti passano comunque, il router semplicemente non "si rivela".

Esercizio 2 · Catturare Tracert con WireShark

Tutorial 2 · Parte pratica

In questo esercizio cattureremo il traffico generato da tracert verso un server pubblico (es. 8.8.8.8, il DNS pubblico di Google). Osserveremo in WireShark come ogni hop genera una coppia di pacchetti: ICMP Echo Request in uscita e ICMP Time Exceeded in ingresso.

📌 Perché usare 8.8.8.8? L'indirizzo 8.8.8.8 è il DNS pubblico di Google, raggiungibile da qualsiasi rete. È un buon target perché risponde ai ping e ha un percorso tipicamente di 10–15 hop. Potete usare anche www.google.com o qualsiasi altro host raggiungibile.

Istruzioni passo-passo

  1. Aprire WireShark e selezionare l'interfaccia attiva Aprite WireShark. Identificate l'interfaccia con traffico (Ethernet o Wi-Fi) e fate doppio click per avviare la cattura. Non impostate ancora nessun filtro: vogliamo catturare tutto.
  2. Aprire il Prompt dei Comandi Premete Win + R, digitate cmd e premete Invio.
  3. Eseguire il tracert Digitate nel prompt: 
    tracert 8.8.8.8
    Il comando ci metterà 30–60 secondi. Lasciatelo completare; vedrete gli hop apparire uno a uno. L'output sarà simile a: 
    Ricerca instradamento per 8.8.8.8 con un massimo di 30 hop:

  1    1 ms    1 ms    <1 ms  192.168.1.1        ← router di casa
  2    8 ms    7 ms    9 ms   10.x.x.x           ← router ISP
  3   12 ms   11 ms   13 ms  x.x.x.x
  ...
 10   18 ms   18 ms   17 ms  8.8.8.8            ← destinazione!
Traccia completata.
  4. Fermare la cattura in WireShark Appena il tracert è terminato, tornate su WireShark e premete ■ Stop (Ctrl+E).
  5. Filtrare i pacchetti ICMP Nella barra dei display filter digitate: 
    icmp
    Vedrete una lunga lista di pacchetti. Individuate:
    • ICMP Echo (ping) request – i pacchetti inviati con TTL crescente
    • ICMP Time-to-live exceeded – le risposte dei router intermedi
    • ICMP Echo (ping) reply – la risposta della destinazione finale
  6. Analizzare un Echo Request Cliccate su uno dei primi ICMP Echo (ping) request e nel pannello centrale espandete:
    • Internet Protocol Version 4 → osservate il campo Time to Live (sarà 1 per il primo hop, 2 per il secondo, ecc.)
    • Internet Control Message Protocol → Type: 8 (Echo Request), Code: 0
  7. Analizzare un Time Exceeded Cliccate su un pacchetto ICMP Time-to-live exceeded e espandete:
    • Internet Protocol Version 4 → l'IP sorgente è quello del router che ha scartato il pacchetto
    • Internet Control Message Protocol → Type: 11 (Time Exceeded), Code: 0
    • Dentro troverete anche il pacchetto originale che ha causato l'errore (incapsulato nell'ICMP)
  8. Filtrare solo i Time Exceeded Provate il filtro avanzato: 
    icmp.type == 11
    Vedrete solo i messaggi di errore dei router. Contate quanti hop hanno risposto (alcuni con * * * non appariranno perché non hanno inviato alcuna risposta ICMP).
  9. Trovare la risposta finale Applicate il filtro: 
    icmp.type == 0
    Type 0 = Echo Reply: vedrete la risposta della destinazione finale (8.8.8.8). Confrontate l'RTT mostrato da tracert con i tempi che potete calcolare in WireShark.

Riepilogo tipi ICMP visti in questo esercizio

Tipo ICMP Nome Inviato da Significato
8Echo RequestPC (tracert)Pacchetto sonda inviato con TTL basso
11Time ExceededRouter intermedioTTL=0, pacchetto scartato → router si identifica
0Echo ReplyDestinazione finaleHost raggiunto, tracert completato
3Destination UnreachableRouter / hostDestinazione non raggiungibile (raro in tracert)
✅ Cosa dovreste vedere in WireShark Per ogni hop del tracert (es. 10 hop = 10 router) dovreste trovare: 3 Echo Request in uscita + fino a 3 Time Exceeded in ingresso (se il router risponde). Alla fine, 3 Echo Reply dalla destinazione 8.8.8.8. Multiplicate per 3 (le tre sonde per hop) e avrete un'idea di quanti pacchetti totali aspettarvi.

Spuntate ogni punto dopo averlo completato:

  • Ho avviato la cattura su WireShark sull'interfaccia corretta
  • Ho eseguito tracert 8.8.8.8 nel Prompt dei Comandi e ho atteso il completamento
  • Applicando il filtro icmp vedo pacchetti Echo Request e Time Exceeded
  • Ho trovato un Echo Request e verificato il campo TTL nell'header IP
  • Ho trovato un pacchetto ICMP Time Exceeded (tipo 11) e identificato l'IP del router che lo ha inviato
  • Con il filtro icmp.type == 11 ho contato quanti router hanno risposto
  • Con il filtro icmp.type == 0 ho trovato la Echo Reply finale da 8.8.8.8
  • Ho confrontato gli hop visti nel cmd con i pacchetti in WireShark
